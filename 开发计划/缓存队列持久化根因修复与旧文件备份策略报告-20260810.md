# 缓存队列持久化根因修复与旧文件备份策略报告

日期：2026-08-10

## 背景

用户复测反馈两点：

1. 上一轮加的"缓存队列跟随工程持久化"功能实测不生效——不管在队列里怎么增删/勾选，关闭工程重新打开后列表永远是空的。
2. 对"渲染前删掉旧缓存文件"这个做法提出异议：逻辑上应该先把上一轮的缓存文件备份（改名 `.bak`），等这一轮渲染并导入成功之后才真正删除备份，而不是渲染前就直接删掉——否则一旦这次渲染失败，上一轮的缓存也丢了。同时用户提出一个待确认的疑虑：工程还开着的时候，旧的 MOV 文件可能被 AE 占着（哪怕已经把对应的 FootageItem 从工程面板摘掉），这种情况下改名/删除会不会失败。

## 分析

### 问题 1：持久化为什么不生效

`OF_Tools_saveCacheQueueForProject` / `OF_Tools_loadCacheQueueForProject` 用的是 `JSON.stringify` / `JSON.parse`，而调用点都包在 `try/catch` 里，异常会被 `OF_Log` 记下来但不会让脚本崩溃。问题在于：**ExtendScript（AE 的脚本引擎）是基于很老的 ES3 规范，不一定自带原生 `JSON` 全局对象**——在没有 `JSON` 的版本上，`JSON.stringify(...)` 会直接抛 `JSON is undefined`，这个异常被 catch 吞掉，`app.settings.saveSetting` 那一行根本没执行到，所以从第一次点保存开始，数据就没有真正写进去过；同理读取那边 `JSON.parse` 也一样会抛异常，直接返回空数组。这和用户观察到的"每次打开都是空的"完全吻合——不是"写了读不出来"，是从头就没写成功。

（这个仓库里 `colorPanel.jsx` 的色板持久化、`cacheFolderPath` 的目录记忆之所以一直正常，是因为它们存的都是纯字符串，没有经过 `JSON.stringify`/`parse` 这一步，绕开了这个坑。）

### 问题 2：旧文件应该先备份而不是直接删

用户的诉求是对的：直接删除是不可逆的，如果这次渲染因为任何原因失败（比如输出模块模板配置错、磁盘写满），上一轮好的缓存也没了。应该改成"改名保留，成功了再删"的两步式操作，把风险窗口从"整个渲染过程"缩小到"只有 import 阶段那一小段"。

关于文件占用的疑虑：`OF_Tools_removeExistingCacheFootage` 在这之前已经把引用这个路径的 `FootageItem` 从工程面板摘掉了，但 AE 内部是否立刻释放对应文件的系统级句柄并不确定（取决于 AE 自己的内存/文件缓存策略，脚本层面没有办法强制它立刻释放）。所以备份这一步不能假设一定成功，需要考虑失败之后怎么办，不能让整个缓存流程因此中断。

## 修复

### 1. 去掉 JSON 依赖（`src/tools.jsx`）

新增 `OF_Tools_encodeCacheQueue` / `OF_Tools_decodeCacheQueue`，用极简的手写格式代替 JSON：每一项编码成 `"id:enabled"`（`enabled` 是 `0`/`1`），多项用逗号连接，比如 `"123:1,456:0"`。解码时按逗号拆开、再按冒号拆开，`parseInt` 转回数字 id，找不到对应 `id` 的项直接丢弃（说明合成已被删除）。整个过程只用到 `split`/`join`/`parseInt`，不依赖 `JSON` 是否存在。

`OF_Tools_saveCacheQueueForProject` / `OF_Tools_loadCacheQueueForProject` 改为调用这两个新函数，并且在成功保存/读取时也打一条 `OF_Log`（带上 key 和实际内容），方便后续如果还有问题，直接从面板日志里看到到底有没有写进去、写的是什么。

### 2. 旧缓存文件改成"备份后延迟删除"（`OF_Tools_cacheOneComp`）

原来的流程：摘除 FootageItem 引用 → 直接 `File.remove()` 删掉旧文件 → 渲染 → 导入。

改成：

1. 摘除 FootageItem 引用之后，如果 `movPath` 对应的文件存在，尝试用 `File.rename()` 把它改名成同目录下的 `<合成名>_cache.mov.bak`（改名前先清掉可能残留的上一次的 `.bak`）。
2. 如果改名失败（最可能的原因就是文件被占用），退回直接 `File.remove()`；如果连删除也失败，就放着不管——后果只是这一次 `renderQueue.render()` 时 AE 会弹出"文件已存在"的确认框，不会导致脚本报错或流程中断，只是没能达成"一键无弹窗跑完"这个优化目标，用日志记录下来方便排查是不是真的遇到了文件占用。
3. 渲染 + 导入都成功之后，才真正删除 `.bak` 备份文件。
4. 如果渲染失败（`rendered` 为 `false`），把 `.bak` 改名还原回原来的文件名，保证这次失败不会导致上一轮的缓存丢失。

这样任何一步失败都有对应的日志和兜底路径，不会因为文件系统层面的意外情况让整个批量缓存流程崩掉。

## 待验证

1. 在 Cache 面板里加入几个合成、调整顺序/勾选状态，保存工程后完全关闭 AE 再重新打开，确认面板日志里能看到 `[CacheManager] 读取缓存队列 key=... 内容=...`，且列表、顺序、勾选状态都正确恢复。
2. 对同一个合成连续缓存两次，确认第二次开始前旧文件被改名为 `.bak`（可以在缓存目录里用文件浏览器观察改名的瞬间，或者看日志里的"旧缓存文件已备份为"），第二次缓存完成后 `.bak` 文件被删掉，只留最新的一份。
3. 故意让第二次渲染失败（比如临时改错输出模块模板名字），确认失败后 `.bak` 被还原成原文件名，缓存目录里保留的是上一轮成功的旧缓存，而不是丢失或留着一个 `.bak` 尾巴。
4. 观察日志里是否出现"旧缓存文件改名备份失败"——如果频繁出现，说明用户之前担心的"工程开着时文件被占用"确实存在，需要再考虑是否要在摘除 FootageItem 和改名之间加一个短暂等待或者其它释放句柄的手段。
