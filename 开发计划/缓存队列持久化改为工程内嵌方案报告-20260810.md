# 缓存队列持久化改为工程内嵌 marker comp 报告

日期：2026-08-10

## 背景

之前两轮修复（去掉 JSON 依赖、改成手写字符串序列化）之后，用户重测确认缓存队列**仍然没有跟随 aep 存储**——关闭工程重开，列表还是空的。根因分析：旧方案把队列存进 `app.settings`（AE 应用级偏好设置，不是工程文件本身的一部分），key 用 `hashString(app.project.file.fsName)` 算；这条路径本身有结构性弱点（未保存工程没有路径直接跳过持久化，`app.settings` 是否在这台机器/这个 AE 版本上跨会话可靠落盘也无法从脚本层面完全确认），继续在这条路径上排查投入产出比不高。

用户提出一个绕开问题的方案：把队列数据直接存成工程里的一个内部合成（marker comp），用它的 layer 顺序编码队列顺序、layer 的 `enabled` 编码是否勾选。这是原生工程数据，`File > Save`/`Open` 天然读写，不依赖工程路径也不依赖 `app.settings`。采纳了这个方案。

## 修复（`src/tools.jsx`）

### 1. 新增内部 marker comp 机制

- `OF_TOOLS_CACHE_QUEUE_COMP_NAME = "_OF_CacheQueue"` + `OF_Tools_isCacheQueueDataComp(comp)`：按名字精确识别这个内部合成。
- `OF_Tools_findCacheQueueComp()`：只找不建，找不到返回 `null`（读取路径专用）。
- `OF_Tools_getOrCreateCacheQueueComp()`：找到就复用（顺手把 `parentFolder` 归位到 `Cache` 文件夹），找不到才新建一个 4x4px/1帧的空合成，挂进 `OF_Tools_getOrCreateCacheFolder()`，并设置 `comment` 提示语（保存路径专用）。
- 新建时额外设置了 `comment`："OF Cache Tool internal data — do not rename, move, or delete."

### 2. 顶层警戒文字层（用户在实现过程中追加的要求）

新增 `OF_Tools_addCacheQueueWarningLayer(markerComp)`：每次重建 marker comp 的层之后，最后再加一个文字层（`layers.addText(...)`），内容是"⚠ 该合成为 visnlink 插件 Cache 队列内部数据，请勿删除/重命名/移动"，同时把这段文字设成图层名（不打开合成、只看 Timeline 图层列表也能看到警告），`locked = true` 防误编辑，`label = 2`（红色）做视觉区分。因为最后添加、`layers.add`/`addText` 都是插到最顶层，这个警戒层天然落在整叠层的最上面。

读取时（`OF_Tools_loadCacheQueueForProject`）不需要特殊跳过这个警戒层——它是文字层，没有 `.source`，`OF_Tools_isCompValid(source)` 检查会自然把它过滤掉，不会被误当成一条队列数据。

### 3. 排除 marker comp，避免被误处理

- `OF_Tools_getSelectedComps()`（Add 按钮的数据源）：`app.project.activeItem` 分支和 `item.selected` 扫描分支都加了 `!OF_Tools_isCacheQueueDataComp(...)` 排除，避免用户点开看了一眼这个内部合成就被当成"当前选中的合成"塞进队列。
- `OF_Tools_replaceParentSource(sourceComp, precomp)`：这个函数会扫描全项目所有合成，把引用 `sourceComp` 的层批量 `replaceSource` 成 precomp——而 marker comp 里的层引用的正是被缓存的原合成，不排除的话每次缓存都会把 marker comp 里对应那层的 `source` 换成 `xxx_pre`，污染持久化数据。在现有 `if(item === precomp) continue;` 后面加了 `if(OF_Tools_isCacheQueueDataComp(item)) continue;`。

### 4. 重写持久化读写，删除旧的 `app.settings` 路径

删除了 `OF_Tools_findCompById`、`OF_Tools_hashString`、`OF_Tools_getProjectQueueSettingKey`、`OF_Tools_encodeCacheQueue`、`OF_Tools_decodeCacheQueue`（全文 grep 确认只在这个区块内部互相引用，没有被其它地方用到，直接删）。

`OF_Tools_saveCacheQueueForProject(cacheItems)`：包一层 `beginUndoGroup("Update Cache Queue")`/`finally endUndoGroup()`，先从上往下删掉 marker comp 现有的所有层，再把 `cacheItems` 倒序依次 `layers.add(entry.comp)`（因为 `add()` 总是插到最顶层，倒序添加后最终顶到底的顺序才等于数组从前到后的顺序），每层设 `enabled = entry.enabled`，最后加警戒层。

`OF_Tools_loadCacheQueueForProject()`：找 marker comp（找不到直接返回 `[]`，不顺手创建），按 `layer(1)..layer(numLayers)` 顺序遍历，取 `.source`，用现有的 `OF_Tools_isCompValid` 过滤掉失效/非合成引用（也顺带过滤掉警戒文字层），按顺序还原成 `{comp, enabled}` 数组。

`OF_Tools_initCachePanel` 里调用 `persist()`/初次加载的地方不需要改任何签名——替换只发生在这两个函数内部。已确认所有 `persist()` 调用点都不在一个尚未关闭的 `beginUndoGroup` 内，新加的 undo group 不会嵌套冲突。

同时去掉了旧代码里"工程未保存则跳过持久化"的早退——marker comp 方案不依赖工程路径，未保存的工程一样能有这个内部合成，之后用户执行 Save 时数据自然落盘。

## 已知取舍

- 队列变成真实工程数据后，面板里每次增删/排序/勾选都会产生一条 Undo 记录（"Update Cache Queue"），并让工程标脏（标题栏出现 `*`）——这是"让队列真正持久化"必然的代价，之前用 `app.settings` 时完全没有这个副作用。
- marker comp 靠名字识别，不是防篡改的：如果用户在 Project 面板手动改名/移动/删除它，或删掉整个 `Cache` 文件夹，队列会读空或者下次保存时另建一个新的（旧的孤立留在原地）。已经加了警戒文字层 + `comment` 双重提示降低误删概率，但没有加更复杂的保护机制（比如锁定合成本身、拦截删除操作），跟现有 `Cache` 文件夹/`_pre` precomp 的脆弱性属于同一类风险，认为够用。
- marker comp 里除了警戒层，其它层引用的是队列里的真实合成，Project 面板缩略图会显示一个很小、被压扁的合成画面，纯外观，因为这个合成待在 `Cache` 文件夹里、默认收起、从不打开查看。

## 待验证

1. Cache 面板加入几个合成、调整顺序、切换勾选，Project 面板 `Cache` 文件夹下应出现 `_OF_CacheQueue` 这个合成，双击打开能看到顶层有红色警戒文字层，下面按顺序排列着各队列合成对应的层。
2. 保存工程、完全退出 AE、重新打开，确认 Cache 面板列表/顺序/勾选状态原样恢复，日志（`[CacheManager] 从缓存队列数据合成读取 N 项`）无异常。
3. 跑一次 Start Cache，确认缓存完成后 `_OF_CacheQueue` 里各层的 `source` 没有被误替换成对应的 `_pre` precomp（验证 `OF_Tools_replaceParentSource` 排除逻辑生效）。
4. 手动选中/双击打开 `_OF_CacheQueue` 本身，回到 Cache 面板点 Add，确认不会被当成"当前选中的合成"加入队列。
5. 确认队列增删/排序/勾选后标题栏出现未保存标记，且 Ctrl+Z 能撤销"Update Cache Queue"这一步而不影响其它编辑历史。
6. 检查警戒层是否会被批量工具（比如"批量开 Motion Blur"之类扫描全部合成/层的工具）误处理——目前排查过的两个高风险点（`getSelectedComps`、`replaceParentSource`）已经排除，但如果后续遇到其它扫描全项目合成的函数，需要补上同样的排除判断。
