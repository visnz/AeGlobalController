# 缓存覆盖确认弹窗与遗留 Undo 告警排查报告

日期：2026-08-10

## 背景

用户用一个很短的合成测过上一轮的 undo group 修复：`Undo group mismatch` 的警告仍然弹出，但功能上 precomp 已经正常建好并替换。同时用户提出实际诉求：因为每次缓存都是往同一个文件名覆盖输出，AE 每次渲染前都会弹"是否覆盖/该文件正被工程使用"的确认框，批量缓存时没法一键跑完，每项都要手动点一次，问能不能从软件设置层面关掉，或者靠改名绕开。

## 分析

这两个现象大概率是同一个根因：**AE 检测到本次渲染的输出路径，正被工程里已导入的旧缓存素材项占用**，于是弹出一个模态确认框。这个模态框是在 `renderQueue.render()` 内部同步弹出的——即使我们已经在上一轮修复里做到"任何 undo group 都不会跨越 render() 调用"，AE 引擎自己在渲染过程中被这个模态框打断，仍然可能导致它自己内部的操作计数和脚本的 undo 记录对不上，从而报出 "Undo group mismatch, will attempt to fix"。也就是说，上一轮修复解决了"脚本自己开的 group 横跨渲染"这个问题，但没有解决"渲染本身被模态框打断"这个问题，而后者才是真正持续触发确认框、以及很可能仍然触发告警的原因。

调研确认：AE 的 DOM/脚本接口没有暴露任何可以关掉"文件已存在"或"该文件正被工程使用"这两个确认框的开关（`app.preferences` 里也没有对应的 key），GUI 里 Output 首选项的"Overwrite files if they exist"选项也不会同步生效到脚本触发的渲染上。业界脚本作者通用的做法是：渲染前把目标路径上的旧文件删掉，并确保工程里没有素材项还占着这个路径。这正好和用户提出的"改名绕开"是同一个思路，只是这里选择"直接摘除引用+删除旧文件"而不是改名保留。

## 修复

`OF_Tools_cacheOneComp()`：把 `movPath` 的计算提前到最前面（原来是在建 precomp 之后才算路径），这样准备阶段就能拿到目标路径。在"准备阶段"的 undo group 内，`OF_Tools_ensurePrecompLayers()` 之后新增一步 `OF_Tools_removeExistingCacheFootage(movPath)`：按文件的 `fsName` 精确匹配（不是按名字，避免误删同名但不同路径的素材），把工程里任何指向这个 movPath 的旧 `FootageItem` 从项目面板里摘除。准备阶段的 undo group 关闭之后，再检查 `movPath` 对应的物理文件是否还存在，存在就直接 `File.remove()` 删掉。这样等真正调用 `renderQueue.render()` 时，工程里没有素材引用这个路径，磁盘上也没有同名文件，AE 没有理由弹确认框。

## 待验证

1. 对同一个合成连续点两次 Start Cache（第二次是覆盖第一次的缓存），确认整个过程不再弹出"文件已存在"或"该文件正被工程使用"的确认框，也不需要手动点确认。
2. 批量勾选多个合成，其中部分是第二次及以后缓存（已有旧 MOV 素材），一次性点 Start Cache，确认能无人值守跑完整个队列。
3. 反复缓存几轮后确认 AE 事件/控制台不再出现 "Undo group mismatch" 警告；如果仍然出现，说明还有别的模态框触发点，需要再排查（比如输出模块模板缺失时的 `alert()`——不过那个在渲染队列 render 之前就应该已经被我们的模板检查挡掉了）。
4. 确认 Project 面板里不会残留多份同名旧缓存素材项（每次缓存后旧的应该已经被摘除，只留最新一份）。
